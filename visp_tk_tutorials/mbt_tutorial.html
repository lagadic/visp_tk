Model-Based Tracker (MBT) tutorial

This is a tutorial for the visp_mbt package. The documentation of the Model-Based Tracker (MBT) provided by ViSP can be found here ViSP documentation also provides step-by-step tutorials to progressively learn how to use the MBT here .

Consequently, this tutorial will not focus on explaining the meaning of the different parameters of the MBT, but instead focus on the specificities on how to use the visp_mbt package.

A node of the visp_mbt package can either be initialized using a JSON configuration file or an XML configuration file. Depending on the type of the configuration file, some parameters of the node must be or must not be set. Consequently, we will study the two cases separately.

Tutorial using a JSON file

Purpose of this tutorial

The purpose of this tutorial is to show how to configure a visp_mbt node using a JSON file. We begin with this kind of file because it is the simplest way of configuring the node. If you have the choice between the XML and the JSON options, we suggest you to use a JSON file. See ViSP tutorial for more information.

How to launch it

If you compiled the packages, you have to source the workspace in which you have compiled the packages. Otherwise, if you installed the packages using the package manager, you only have to source the /opt/ros/${ROS_DISTRO}/setup.bash file (or one of the other setup files if you are not using bash).

Then you can run:

ros2 launch visp_tk_tutorials mbt_laas_box_bag_json_launch.py

The launch file accepts different arguments. To have the list and the explanations related to the arguments, please run:

ros2 launch visp_tk_tutorials mbt_laas_box_bag_json_launch.py --show-args

Using another configuration file

The settings of the tracker (visual features, moving edges and KLT parameters, camera, clipping…) are given by the configuration file passed with the config_file launch argument. It must be an absolute path. To use a file installed with the package, you can build this path with ros2 pkg prefix. For instance, to run the same tutorial with a copy of laas_box.json that you modified:

cp $(ros2 pkg prefix visp_tk_tutorials)/share/visp_tk_tutorials/config/mbt/laas_box/laas_box.json /tmp/my_box.json
# Edit /tmp/my_box.json, then:
ros2 launch visp_tk_tutorials mbt_laas_box_bag_json_launch.py config_file:=/tmp/my_box.json

The configuration files provided with the package are described in a README.md file next to them:

  • config/mbt/laas_box/: laas_box.json and laas_box.xml, to track the box of this tutorial with the color camera;

  • config/mbt/teabox/: teabox.json, to track a teabox with a RealSense color and depth camera (see Tutorial using a Realsense camera). It requires a depth stream, which the recorded sequence of this tutorial does not provide;

  • config/mbt/cube/: cube.json, to track the textured cube with a RealSense color and depth camera (see Tracking another object with the camera);

  • config/mbt/castle/: castle.json, to track the castle with a RealSense color and depth camera (see Tracking another object with the camera).

When the tracked object changes, the 3D model and the initialization points must change too: in a JSON file, the model is given by the model key, and the file giving the points to click at initialization by the init_file launch argument.

If a file does not exist, the tracker cannot be initialized: the node displays an error, stops, and the launch file ends.

As you can see, the generate_launch_description() method mostly declare the launch arguments and register an OpaqueFunction object that will be called once the context of the launch file will be known. However, it is important to notice that it also sets an OpenMP environment variable. It helps accelerate the processing of depth images when the depth stream is used too.

Tutorial using an XML file

Purpose of this tutorial

The purpose of this tutorial is to show how to configure a visp_mbt node using an XML file. If you have the choice between the two options, we suggest you to use a JSON file instead, but you may not have the possibility if ViSP has not been compiled with the required dependency. See ViSP tutorial for more information.

How to launch it

If you compiled the packages, you have to source the workspace in which you have compiled the packages. Otherwise, if you installed the packages using the package manager, you only have to source the /opt/ros/${ROS_DISTRO}/setup.bash file (or one of the other setup files if you are not using bash).

Then you can run:

ros2 launch visp_tk_tutorials mbt_laas_box_bag_xml_launch.py

The launch file accepts different arguments. To have the list and the explanations related to the arguments, please run:

ros2 launch visp_tk_tutorials mbt_laas_box_bag_xml_launch.py --show-args

Tutorial using a Realsense camera

Purpose of this tutorial

The purpose of this tutorial is to show how to configure a visp_mbt node when using an RGBD sensor. We chose to use a Realsense RGBD sensor, and deliberately chose not to require the depth stream aligned with the color stream in order to show you how to face such a situation.

How to launch it

If you compiled the packages, you have to source the workspace in which you have compiled the packages. Otherwise, if you installed the packages using the package manager, you only have to source the /opt/ros/${ROS_DISTRO}/setup.bash file (or one of the other setup files if you are not using bash).

Then you can run:

ros2 launch visp_tk_tutorials mbt_teabox_live_rs2_json_launch.py

The launch file accepts different arguments. To have the list and the explanations related to the arguments, please run:

ros2 launch visp_tk_tutorials mbt_teabox_live_rs2_json_launch.py --show-args

Tracking another object with the camera

mbt_cube_live_rs2_json_launch.py tracks the textured cube (0.085 m edges) instead of the teabox, with the same camera setup. It uses config/mbt/cube/cube.json, which has the same settings as teabox.json with the model of the cube: moving edges and KLT keypoints, tracked on the drawings of the faces, for the Color tracker, and depthNormal for the Depth tracker. The object frame and the initialization points (cube.init) are the same as for the RBT model of the cube (config/rbt/models/cube).

ros2 launch visp_tk_tutorials mbt_cube_live_rs2_json_launch.py

mbt_castle_live_rs2_json_launch.py tracks the castle with config/mbt/castle/castle.json. Its Color tracker has the same settings as teabox.json, but its Depth tracker uses depthDense features instead of depthNormal: the castle has few planar faces, partly occluded, and the many depth points sampled on them constrain the pose better when the object moves. The RBT model of the castle is a scanned mesh of about 36 000 triangles, which the MBT cannot use. castle.cao is a simplified model made of the planar parts of the castle seen from the front: the floor, the walls of the tower, the front wall with the door and the slope. Each part is described in its own file of config/mbt/castle/castle_parts/, that castle.cao includes with load(). The initialization points (castle.init) are shown on castle.jpg, the same image as for the RBT, but their coordinates are expressed in the object frame of this model, which is not the one of the RBT model.

ros2 launch visp_tk_tutorials mbt_castle_live_rs2_json_launch.py

If nothing appears on screen, it may mean that the realsense_camera package changed the names of the topic on which are published the data. Please run ros2 topic list and ros2 topic info -v /<camera_topic> to check if the realsense_camera publisher and the mbt_node subscriber are both listed. If not, please change the topic names accordingly.

Using another configuration file with the camera

As with the recorded sequence, the configuration file is given by the config_file launch argument. By default, it is teabox.json, which combines a Color tracker (moving edges and KLT keypoints) and a Depth tracker (depthNormal). Its parameters are described in config/mbt/teabox/README.md. To use a modified copy:

cp $(ros2 pkg prefix visp_tk_tutorials)/share/visp_tk_tutorials/config/mbt/teabox/teabox.json /tmp/my_teabox.json
# Edit /tmp/my_teabox.json, then:
ros2 launch visp_tk_tutorials mbt_teabox_live_rs2_json_launch.py config_file:=/tmp/my_teabox.json

The names of the trackers in the JSON file (Color and Depth) must match the first element of the reference_tracker and other_tracker launch arguments, used to get the extrinsics between the two cameras.

Before starting the camera and the tracker, this launch file checks that the files given by config_file, init_file, rgb_model_file and depth_model_file exist (the empty ones are ignored). If one of them does not, the launch file ends immediately with an explicit error, for example:

[ERROR] [launch]: Caught exception in launch (see debug for traceback): Launch argument 'config_file': file '/path/to/file.json' does not exist

157            "depth_module.profile": "640,480,30",  # name used by realsense2_camera <= 4.54

The camera driver (realsense2_camera::RealSenseNodeFactory) and the tracker (visp_mbt::MBTTracker) are loaded as components in the same container, with intra-process communication enabled, so that the color and depth images are passed to the tracker without going through DDS. The container must be single-threaded: the ViSP displays used by the tracker must always be used from the thread that created them.

In the parameters of the camera component, we explicitly ask not to align the depth stream with the color stream, and to publish the TFs in order to have the transform between the frames of the two sensors (the color one and the depth one).

272        ## [Launch argument for aligning streams, color stream]
273        DeclareLaunchArgument(
274            "reference_tracker",
275            description="When set, the extrinsics will be loaded from a TF2 topic and this parameter must be a vector of size 2 such as [\"${REF_TRACKER_NAME}\",\"${REF_TRACKER_FRAME_NAME}\"]. The parameter ``other_tracker`` becomes **REQUIRED**.",
276            default_value="[Color,camera_color_optical_frame]"
277        ),

By telling that the reference_tracker is the Color one, we mean that the tracking results will be expressed with regard to the color sensor. We then give the name of the frame that corresponds to the color sensor.

260        ## [Launch argument for aligning streams, depth stream]
261        DeclareLaunchArgument(
262            "other_tracker",
263            description="When set, the extrinsics will be loaded from a TF2 topic and this parameter must be a vector of size 2 such as [\"${OTHER_TRACKER_NAME}\",\"${OTHER_TRACKER_FRAME_NAME}\"]. The parameter ``reference_tracker`` becomes **REQUIRED**",
264            default_value="[Depth,camera_depth_optical_frame]"
265        ),

By telling that the other_tracker is the Depth one, we mean that the tracking features of the depth frame will be translated into the frame of the color sensor. We then give the name of the frame that corresponds to the depth sensor to extract the extrinsics from the TFs that are published.

Display of the object frame

When the tracking succeeds, the frame of the object is displayed on the image, with its X, Y and Z axes in red, green and blue. Its size and thickness can be changed with two launch arguments, accepted by all the launch files of this package:

Launch argument

Default

Meaning

frame_size_ratio

0.3
Length of the axes, as a fraction of the object diameter,
i.e. the diagonal of the bounding box of the 3D model.
The axes are never shorter than 30 pixels, so that they stay
readable when the object is far from the camera.

frame_thickness

2
Thickness of the axes, in pixels.

For instance:

ros2 launch visp_tk_tutorials mbt_laas_box_bag_json_launch.py frame_size_ratio:=0.2 frame_thickness:=3
